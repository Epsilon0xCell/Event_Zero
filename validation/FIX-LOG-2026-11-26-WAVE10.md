- W1. tests/test_accuracy_audit_fixes.py (gcc test): the test

## Item 1: the line ledger accounts ordinary structure and data lines

All changes are in event_zero/families.py, in
script_line_ledger and its helpers. The classification order
is unchanged where it matters: the flagged scan (download,
tamper, persistence, exfiltration atoms) still runs before any
structural or data classification, so a hostile atom on any of
the newly accounted shapes is flagged, never accounted away.

1a. Ordinary statement keywords. The structural pattern now
includes the remaining ordinary Python statement keywords:
pass, break, continue, raise, assert, del, global, nonlocal,
yield, await, async. A bare `pass` is ordinary structure in
every dialect that has it; it was simply missing from the
list.

1b. Expression statements, with callee resolution. A line that
is a single expression statement is structural when the ledger
can fully read it: with string literals removed, the remainder
is names, attribute and index access, calls and operators,
with balanced delimiters, at least one call, no top-level
assignment and no compound header; AND every call it makes
resolves to a name whose behaviour is fixed by what the file
shows: a function or class defined in this file, a name this
file imports (the known-names set now collects def, class and
import bindings), an attribute of a visible receiver chain, or
a builtin whose behaviour is fixed by its name. The
dynamic-execution builtins (eval, exec, compile, __import__,
getattr, setattr, delattr) are excluded from the builtin set:
what they run is chosen by data, so a line calling them is not
accounted from the line. The same expression was already
accounted when it followed return or an assignment target;
standing alone it is the same ordinary structure (the backup
twin's open(...).write(...) chain and os.remove(...)).

Development correction, recorded: the first version of this
rule accounted any well-shaped call expression, including a
bare call to an undefined name. The existing test
test_defect4_unaccounted_line_blocks_no_for_any_script caught
it: a call to a name the file does not define or import stays
unaccounted (accuracy audit defect 4: what that name does
cannot be known from this file). The callee-resolution
requirement above is the tightening, and the defect 4 test
passes unmodified.

1c. Phrase-key declarations. A structural pattern now matches
a declaration whose key is two or more space-separated words
(`app name = BandwidthShare`): never valid code in any dialect
the ledger serves; it is the config and data-sheet shape. The
value side is constrained to data characters (no call,
substitution or second assignment), so the pattern cannot
account a command line such as `run-me --output=$(evil)`.
That constraint was added after a new wave 10 test caught the
unconstrained pattern matching exactly that shape.

1d. Data lines. A new accounted class (counted as "data" in
the ledger record): a line of whitespace-separated literal
tokens (bare words, numbers, versions, URLs, paths, flag
tokens) containing no call, quote, operator, substitution,
glob or chaining character. Such a line can only name things:
read as data it declares exactly those tokens, and read as a
command its program and arguments are the same literal
tokens, so nothing it can do is hidden from the ledger.
Interpreter-proxy invocations written this way (a bare
`powershell -EncodedCommand <blob>` line, probed directly)
remain capped by the verdict's own R5 proxy rule, which is
independent of the ledger; the ledger's flagged atoms remain
capped by the flagged scan. Lines with shell metacharacters
stay unaccounted (probed: `x -> y -> z`,
`run-me --output=$(evil)`, a bare `*.txt` glob).

1e. Semicolon comments. A leading-semicolon line is a comment
in the INI, registry and assembler dialects. It is classified
as data only after the flagged scan has run over the whole
line, so a hostile atom after the semicolon is flagged, never
commented away (tested), and only when the remainder is
itself accounted as data or structure.

## Item 2: the parse-failure attribution rule

The exact rule implemented (event_zero/verdict.py, in the
wave 3 R3 block, using script_parse_failure_attribution from
event_zero/families.py):

The script-parse-failure incompleteness cap is NOT added when
both of the following hold:
(1) the file's line ledger accounts for every non-blank line
(its unaccounted list is empty); and
(2) the parse failure is attributable to non-code lines:
recompiling the source while replacing each successive
syntax-error line with a bare pass at the same indentation
reaches a clean compile, where every replaced line is a plain
statement line (not a compound-statement header, not a
decorator), and no error is of the unterminated-string,
unclosed-delimiter, EOF or indented-block class.
Otherwise the cap stands exactly as before. When the cap is
suppressed, the file record carries a script_parse_attribution
note naming the neutralised lines, so the reasoning is on the
record, not silent.

Why this is the right line: the three capped twins are not
Python programs; they are data sheets in .py files, and every
line the parser choked on is a line the ledger accounts as
data. The wave 3 test case is the opposite: `def broken(:` is
a malformed code line, a compound header whose body the
parser never examined, so condition (2) refuses it and the
cap stands (test_wave3_python_parse_error_blocks_no passes
unmodified, as does a new wave 10 test where a parse failure
and a ledger-unaccounted line coexist and both caps fire).
An unterminated string or unclosed delimiter means content
was swallowed or structure is missing, which no per-line
classification can account for; those classes are never
attributable.

## Item W1: the gcc test requests the name the toolchain produces

tests/test_accuracy_audit_fixes.py,
test_defect13_gcc_elf_not_flagged_safengine (the one changed
existing test): the output is now requested as hello.exe on
Windows (os.name == "nt") and hello elsewhere, which is the
name MinGW gcc actually produces in each case; if gcc reports
success but no output exists at that path, the test skips
with a named reason instead of failing on the open.
Justification: the test encoded the platform defect itself
(a fixed extensionless output name); the engine behaviour it
verifies (a gcc-built ELF is not flagged as a virtualised
protector) is unchanged.

## Item W2: the gate reports even when host extraction fails

event_zero/verdict.py, in enumerate_subject's expand(): when
ZIP or TAR extraction raises and the container is recorded as
failed, the member-semantics gate is run on the archive bytes
and its divergences are attached to the container's own
record (entry_blockers) with the same blocker text the
enumerated path uses. The container still caps as
could-not-enumerate; what changes is that the member kinds
(stream-qualified-name, path-traversal-backslash, and the
rest) are computed from the archive and reported identically
on every host, instead of the classification being rewritten
by a host filesystem error. Verified here by a unit test that
simulates the Windows extraction failure (the extractor
raising Errno 22) and requires stream-qualified-name to reach
the enumeration record.

## Item W3: the gate classifies stored names, not listing names

event_zero/coverage5.py, zip_member_semantics: member names
are now read from the central directory bytes (the existing
_zip_central_names walk, hoisted and reused for the
local-versus-central checks), decoded with the same codepage
rule zipfile uses (UTF-8 when the flag bit is set, CP437
otherwise) but with no separator rewriting; the zipfile
listing name is the fallback where the central walk is
unavailable. All divergence classes (name divergences,
duplicates, links, local-versus-central) consume the stored
names, so a backslash traversal is path-traversal-backslash
on every host. Verified here by a unit test that rewrites the
infolist names to the Windows listing form (forward slashes)
and requires the gate to return path-traversal-backslash, and
not path-traversal, from the stored bytes.
