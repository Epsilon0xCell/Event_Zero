Event Zero: malware analysis, two modes

Event Zero is my malware analysis tool. I built it because I wanted to look at a suspicious file and get a straight answer about what is inside it, without handing the file to a website and without running it.

It works two ways. Local mode is pure Python standard library: it reads the sample as bytes, never executes it, and works offline with nothing to install. Autonomous mode builds a BlackArch container and lets Gemini direct standard analysis tools over several rounds, then writes a JSON report.

I wrote the local engine to compute everything from the bytes in front of it. Nothing is guessed and nothing is sent anywhere. The report even states its own limits: static analysis only, and a file with no indicators is not a proven safe file.

sample handling: read as bytes, never executed  |  network in local mode: none  |  dependencies in local mode: zero

$ what the local engine actually computes

hashes
MD5, SHA-1, and SHA-256, calculated directly from the file bytes.
format parsing
Real header parsing for Mach-O (including fat binaries, segments, sections, and linked libraries), ELF (class, machine, object type), and PE (machine, PE32 or PE32+, section names). ZIP, PDF, scripts, and plain text are identified by signature.
entropy
Whole-file Shannon entropy, with the caveat printed in the report when a format carries large zero-padded regions.
strings
Printable ASCII and UTF-16LE strings, extracted from the bytes.
indicators
URLs and IP addresses found in strings, plus hits against a built-in suspicious-keyword watchlist. Presented as leads, not proof.
eicar
Detection of the EICAR anti-malware test file by its known SHA-256.
assessment
A short rule-based summary of the findings, which states its own limits inside the report.

$ the two modes, side by side

Local modeAutonomous mode
NeedsPython 3.8 or newer. Nothing else.Docker running, plus a Google Gemini API key.
DoesOffline static analysis in pure standard library Python.Builds a BlackArch container, copies the sample in, and iterates: Gemini proposes analysis code, it runs in the container, results come back, until the model marks the analysis complete or the iteration cap (default 50) is hit.
FallbackNot needed. It either reads the file or fails cleanly with a reason.If the API fails repeatedly, a built-in fallback performs basic static analysis inside the container instead.
WritesA JSON report next to where you ran it, or the path you pass with --output.autonomous_analysis_report with a timestamp. The container is stopped and removed; the image is kept for reuse.
Exit codes0 on success, 1 on a clean explained failure (missing file, missing API key, Docker unavailable), 2 on bad command line arguments.

fake_malware is a small Mach-O ARM64 executable I built as the test sample, and it is real executable code, not inert text. It carries planted strings (192.168.1.100, 127.0.0.1, a fake credential line, a socket symbol) for local mode to find, and if it is executed it also performs its simulation: system information and a process list written under /tmp, a persistence script created in /tmp, and a connection attempt to 127.0.0.1:4444. Every observed effect is confined to /tmp and loopback and no external destination was found, but the audit was static, with no disassembler available, so treat it as live sample code and never run it outside a controlled analysis environment. Local mode never executes it; it reads and analyzes the bytes.

$ where it stands, honestly

Local mode never runs the sample. Autonomous mode runs analysis tooling against the sample inside a container. For genuinely hostile files, my own README says it and I will say it here too: use a hardened, network-isolated VM, not a workstation.

The keyword watchlist produces leads, not verdicts. I present it that way in the report because that is all static analysis can honestly give, and I would rather understate a finding than dress one up.
